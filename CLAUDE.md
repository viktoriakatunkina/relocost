# Relocost.ru — контекст проекта для Claude Code

Этот файл автоматически подхватывается Claude Code как постоянный контекст проекта.
Он собран 2026-10-19 по факту текущего состояния кода/инфраструктуры — не по памяти и не по старой документации. README.md к этому моменту был устаревшим (описывал хостинг на Vercel, которого уже больше года как нет) — если где-то в проекте встретится противоречащая этому файлу информация, доверяй этому файлу или проверяй по факту (`git log`, живой `curl` на прод, SSH на VPS).

## Что это за проект

SEO-сайт-калькулятор стоимости жизни для людей, планирующих переезд (внутри России и за рубеж). Freemium-монетизация: базовый расчёт бесплатно, детальные пакеты (места/расходы/всё включено) — разовая оплата через ЮKassa. 238 городов, ~85 стран, несколько тысяч статей блога, ~120 новостей.

Домен: **https://relocost.ru**

## Реальный стек (НЕ Vercel)

- Next.js 14.2.35, App Router, SSG (генерация 3300+ статических страниц при билде)
- TypeScript + Tailwind CSS
- Supabase (PostgreSQL) — основная БД
- **Самохостинг на VPS** через `next start` + systemd, НЕ Vercel (несмотря на то что в README написано обратное — это легаси-текст с июня, хостинг сменили)
- ЮKassa — оплата, НПД-чеки для самозанятого
- Unsplash API — фото городов (с оговоркой, см. ниже про недоступность с VPS)
- Cloudflare R2 — часть фото (та же оговорка)
- Anthropic Claude API — генерация SEO-текстов (из скриптов, не из рантайма сайта)
- Яндекс.Метрика — счётчик `109622218`

## Структура репозитория

- `app/[locale]/` — страницы (i18n: ru/en/uz, next-intl)
- `app/api/payment/` — создание/вебхук/верификация оплаты ЮKassa
- `components/` — UI-компоненты
- `lib/` — чистые данные и хелперы (`packages.ts` — цены, `visa.ts` — визовые данные, `photo.ts` — логика выбора URL картинки, `cities-content.ts` — контент городов, `yokassa.ts` — клиент ЮKassa)
- `config/blog-redirects.json` — 301/308 редиректы для схлопнутых/переименованных статей, читается `middleware.ts`
- `scripts/` — одноразовые и переиспользуемые Node-скрипты (seed городов, бэкафилл фото, миграции данных) — почти все пишут напрямую в Supabase через `SUPABASE_SERVICE_ROLE_KEY`
- `supabase/migrations/` — SQL-миграции схемы (13 штук на 2026-10-19)
- `deploy.sh` / `deploy-lowmem.sh` — деплой на VPS (см. ниже)

### ⚠️ `scripts/` читают ключи НЕ из `.env.local`

Сам сайт (Next.js рантайм) берёт ключи из `.env.local` как обычно. Но подавляющее большинство Node-скриптов в `scripts/` (а их 1600+ — это сид городов, фото-бэкафилл, контент-миграции — основная масса операционной работы над проектом) читают ключи напрямую из отдельных файлов в домашней папке: `~/.relocost/<имя>` — например `~/.relocost/supabase_service_role_key`, `~/.relocost/unsplash_access_key`, `~/.relocost/yandex_metrika_token`. Каждый файл — просто текст со значением, без кавычек. Паттерн в коде скриптов обычно такой:
```js
const KEY = fs.readFileSync(os.homedir() + '/.relocost/some_key', 'utf8').trim();
```
Если `.env.local` настроен, а эта папка — нет, сайт будет работать, а скрипты из `scripts/` — нет (упадут с ENOENT). Список нужных файлов и как их создать на новой машине (включая Windows) — см. отдельный файл с доступами, который тебе передали отдельно от репозитория (не в git).

## Деплой — САМОЕ ВАЖНОЕ, прочитать перед первым деплоем

**Хостинг — не Vercel.** Прод живёт на VPS reg.ru (`168.222.143.151`), процесс — `next start` под systemd (`relocost.service`), порт 3000 за nginx. Деплой — через `./deploy.sh` (обычная машина) или `./deploy-lowmem.sh` (если локально ≤8 ГБ RAM — билд 3300+ страниц легко уходит в OOM на полном `--max-old-space-size`).

### Как работает деплой (`deploy.sh`)
1. `npm run build` локально — полная пересборка всех статических страниц (10-40 минут в зависимости от машины/нагрузки)
2. Заливка `.next/` на сервер в **staging**-папку `.next.incoming` (НЕ в живую `.next` напрямую) — rsync
3. Атомарная замена: `.next` → `.next.old`, `.next.incoming` → `.next`, restart systemd
4. Health-check (`curl` до `relocost.ru`, retry ~20с) — если сайт не поднялся, **автоматический откат** на предыдущий билд
5. При успехе — `.next.old` становится `.next.prev` (для ручного `./deploy.sh --rollback` позже)
6. IndexNow-пинг Яндекса/Bing (throttle 8 часов — см. `scripts/indexnow.mjs`)

Рантайм-файлы `.env.local` и `next.config.mjs` на сервере — не трогаются деплоем, живут там отдельно (деплой синхронизирует только `config/` и `next.config.mjs`, не секреты).

### Критичные правила, которые стоили часов отладки в прошлом

1. **Никогда не запускать два `next build`/`deploy.sh` одновременно** — они делят один и тот же `.next` и портят друг друга. Перед деплоем: `pgrep -fl "next build\|npm run build\|deploy.sh"`. **С 2026-10-19 деплоить может больше одного человека** (Виктория/Claude Code и Паша, оба с независимым SSH-доступом на VPS) — это правило теперь касается не только параллельных процессов на одной машине, но и координации между людьми: прежде чем запускать `./deploy.sh`, стоит убедиться, что второй человек не деплоит прямо сейчас (например, написать в чат "деплою"). Признак чужого активного деплоя — `ssh root@168.222.143.151 "ls /opt/relocost/.next.incoming 2>/dev/null"` вернёт что-то (staging-папка существует только во время заливки).
2. **Деплой может зависать часами без кода-причины.** Три независимые причины уже ловили: (a) перегрузка локальной машины (`uptime` — если load average намного выше числа ядер, билд просто медленный, не сломан, ждать); (b) VPS получает постоянный SSH-брутфорс от ботов на 22 порт — не взлом, фоновый интернет-шум, иногда переполняет очередь sshd и рвёт легитимные соединения — просто повторять; (c) старый macOS rsync 2.6.9 иногда криво парсит `-e "ssh ..."` под нагрузкой — уже пофикшено через `RSYNC_RSH` (переменная окружения) + `retry()`-обёртку на 5 попыток в самих скриптах. Если видишь обрыв связи с VPS посреди деплоя — это почти всегда сетевая нестабильность, не баг кода; `retry()` обычно справляется сам, иногда нужно просто перезапустить `./deploy.sh` целиком.
3. **`--rollback`**: `./deploy.sh --rollback` откатывает на `.next.prev` без пересборки за секунды.

### ⚠️ VPS — общий сервер, НЕ только Relocost

`168.222.143.151` хостит одновременно: `relocost`, `foodlore`, `lunarika`, `moto-mobile`, `pulse-mobile`, `vernomer`, `zt-mobile` (+ его API и блог) — всё в `/opt/<project>`, все от root. SSH-ключ, которым обычно пользуются для Relocost (`~/.ssh/relocost_vps`), — это **общий админский ключ**, не relocost-only, несмотря на имя файла. Любой, кто получил этот конкретный приватный ключ, получает root на ВСЁ, что на сервере, а не только на Relocost. См. раздел "Доступы" ниже про то, как выдать доступ новому человеку безопаснее.

## База данных (Supabase)

Ключевые таблицы: `cities` (238 городов), `prices` (цены по категориям на город), `blog_posts` (статьи, поле `content_md`), `news_items`, `purchases` (оплаты), `email_leads`.

**Критичный урок: `blog_posts.content_md` в живой БД может быть НОВЕЕ локального `.md`-бэкапа в `content/blog/`.** Если точечно правишь существующую статью — сначала читай live `content_md` из Supabase, не перезаписывай его локальным файлом вслепую (бывали расхождения на сотни символов после каких-то ad-hoc правок).

Скрипты читают `.env.local` и подключаются через `SUPABASE_SERVICE_ROLE_KEY` (обходит RLS полностью) — обычный паттерн для сид/бэкафилл-скриптов в этом проекте, не считается чем-то необычным здесь, но ключ соответственно мощный.

## Цены и пакеты — ОДНО место истины

`lib/packages.ts` (`CITY_PACKAGES`, `COUNTRY_PACKAGES`) — единственное место, где должны жить цены. Текущие (с 2026-10-14): places 79₽, budget 99₽, bundle 129₽, country_overview 79₽, country_cities 99₽.

**2026-10-14 был критический баг**: `lib/yokassa.ts` когда-то задублировал цены в собственной константе `PACKAGE_PRICES`, независимой от `lib/packages.ts`. Когда цены поменяли в одном месте, второе не обновили — 9 дней сайт ПОКАЗЫВАЛ одну цену, а при оплате СПИСЫВАЛ другую (в разы больше). Уже пофикшено — `PACKAGE_PRICES` теперь вычисляется из `CITY_PACKAGES`/`COUNTRY_PACKAGES`. При любой будущей правке цены: `grep -rn "price\|PRICE" lib/yokassa.ts app/api/payment/` — чтобы убедиться, что не завёлся третий независимый источник.

## Картинки — есть нюанс с доступностью хостов с VPS

С этого конкретного VPS (reg.ru, видимо гео/роутинг-особенность) **ненадёжно или совсем недоступны** по HTTPS: `images.unsplash.com` напрямую, иногда Cloudflare R2, иногда даже сам Supabase Storage бывает подвисает. Next.js по умолчанию прогоняет внешние картинки через серверный оптимизатор (`/_next/image`) — если сервер не может их скачать, это виснет на ~10с и роняет страницу в 500 (было причиной нескольких провалов трафика).

Паттерн-фикс уже применён везде, где рендерятся картинки из этих источников: `lib/photo.ts` экспортирует `isR2Src()`/`isUnsplashSrc()`, и каждый `<Image>` для таких URL получает `unoptimized={isR2Src(x) || isUnsplashSrc(x)}` — это отключает серверную оптимизацию, браузер пользователя качает оригинал напрямую, VPS не участвует. **Если добавляешь новое место, где рендерится фото города/статьи — повторяй этот паттерн**, иначе рискуешь воспроизвести тот же класс бага.

## Контентная честность — принципиальные правила проекта

- **Не выдумывать факты.** Цены, визовые условия, даты — только из реальных источников. `lib/visa.ts` — `VISA_SOURCES` с датированными ссылками на официальные источники (типа kdmid.ru), это обязательный паттерн для новых стран.
- **Никаких фейковых отзывов/рейтингов, выданных за реальные.** Раньше на страницах городов были полностью вымышленные "отзывы переехавших" с именами/рейтингом/датами — признаны риском (38-ФЗ "О рекламе"/практика ФАС) и релейблены как явно иллюстративный контент (без имён, рейтингов, точных дат) с явным дисклеймером. **Для новых городов раздел отзывов вообще не добавляется** — паттерн намеренно не тиражируется дальше.
- **"Е" вместо "ё"** — везде в тексте сайта (сквозное правило по всем проектам Виктории, не только Relocost).
- При добавлении "личных историй" (формат "от первого лица") — обязателен открывающий дисклеймер, что это иллюстративный композит, а не задокументированный реальный человек (если нет реального человека, стоящего за текстом).

## Аналитика

Яндекс.Метрика, счётчик `109622218`. API токен — `~/.relocost/yandex_metrika_token` (не в репозитории). **Важно**: цифры API Метрики за последние 1-2 дня систематически занижены (данные "доезжают" за 1-3 дня) — не делать выводов о провале трафика по свежим дням без проверки через пару дней. Также API включает краулеров (после каждого деплоя идёт IndexNow-пинг, трафик ботов заметно завышает сырые визиты) — метрика "Search engine traffic" (органика) надёжнее сырых "visits".

## SEO-механика

- `config/blog-redirects.json` + `middleware.ts` — 301/308 редиректы для слитых/переименованных статей
- `scripts/indexnow.mjs` — пинг Яндекса/Bing после деплоя, throttle 8 часов, state-файл `.indexnow-last-sent`
- `permanentRedirect()` на уровне страницы (ISR/SSG) в этом проекте фактически отдаёт 307, а не 308 (баг фреймворка/конфигурации) — для редиректов, где важен именно 308, делать их в `middleware.ts` через `NextResponse.redirect(url, 308)`, не на уровне страницы.

## Раздел /news — allow-list категорий (обязательно для новых seed-скриптов)

2026-10-29 (аудит #news-off-topic-content): на эту дату 84% опубликованных новостей (106 из 126) оказались НЕ релокационной тематикой (Технологии/Наука/Спорт/Культура/Политика/Война/Климат/Происшествия и т.п.) — генерик мировые новости вместо тематики переезда. `/news` задумывался как мостик к продукту («новость → посчитайте бюджет»), а не как новостной агрегатор про всё на свете.

**Любой новый `scripts/seed-*-news-*.mjs` (или его преемник) обязан импортировать `scripts/lib/news-categories.mjs` и вызывать `assertAllowedCategory(category, title)` для каждой новости перед записью в `news_items`** — чтобы новые статьи не плодили off-topic контент дальше. Allow-list сейчас: «Визы», «Иммиграция», «Недвижимость». Расширять его — только если новая категория прямо про переезд/жизнь в новой стране, не "around the topic".

Уже опубликованные 106 off-topic новостей этим не затрагиваются — их unpublish/рекатегоризация — отдельное решение Виктории, не автоматизация.

Отдельно: CTA-фраза, которую seed-скрипты дописывают в конец `content_md` («...посчитайте точный бюджет жизни в новом городе на Relocost.»), раньше была простым текстом без ссылки — упоминание бренда никуда не ведёт. Страница статьи (`app/[locale]/news/[slug]/page.tsx`) сейчас оборачивает «Relocost» в реальную ссылку на лету при рендере (`linkifyRelocostMention()`, без миграции БД) — но новым seed-скриптам лучше сразу писать markdown-ссылку в `content_md` (`на [Relocost](https://relocost.ru).`), чтобы не зависеть от этого рантайм-патча.

## Доступы для нового разработчика (Паша) — что нужно и как лучше выдать

Полный список переменных окружения — в `.env.example`. Значения — НЕ в репозитории (секреты), их нужно передать отдельно, вне git.

| Сервис | Зачем | Как лучше выдать |
|---|---|---|
| GitHub (`viktoriakatunkina/relocost`, публичный) | Клонировать код, коммитить | Добавить как collaborator в настройках репозитория на github.com — у него должен быть свой GitHub-аккаунт |
| Supabase | БД, контент | Через Supabase Dashboard → Project Settings → Team — пригласить его email как участника проекта. Так у него будет свой доступ, не нужно передавать `SUPABASE_SERVICE_ROLE_KEY` вручную |
| VPS (деплой) | `./deploy.sh` | **Рекомендую**: Паша генерирует свою пару ключей (`ssh-keygen -t ed25519 -f ~/.ssh/relocost_vps`), присылает только публичный ключ — его добавляют в `/root/.ssh/authorized_keys` на сервере. Так не передаётся общий приватный ключ (который = root на 8+ других проектов), и доступ можно отозвать точечно, не трогая остальных. Более быстрый, но менее безопасный вариант — отдать ему тот же `~/.ssh/relocost_vps`, который используется сейчас (тогда он получит root и на остальные проекты на сервере тоже) |
| ЮKassa | Видеть оплаты/рефанды | Это ключ от реального платёжного шлюза, привязанного к самозанятости Виктории. Проверить в личном кабинете ЮKassa, есть ли роль "только просмотр"/дополнительный пользователь — если нет, нужно явное решение Виктории, давать ли этот ключ вообще, и что с чеками НПД (они идут от её имени как самозанятой) |
| Яндекс.Метрика | Статистика | Добавить его Яндекс-аккаунт представителем счётчика через интерфейс Метрики (Настройки → Доступ) — не требует передачи OAuth-токена |
| Unsplash / Anthropic API ключи | Фото-скрипты, генерация текста | Обычные API-ключи, не завязаны на личность — можно передать напрямую или завести отдельные под Пашу |

**Также:** заход в Claude Code под одним общим аккаунтом (а не под своим) означает отсутствие разделения "кто что сделал" и то, что компрометация его ноутбука = компрометация твоего аккаунта целиком. Если у Claude Code/Claude есть вариант завести ему отдельный аккаунт — это надёжнее. Если решение — именно общий аккаунт, это тоже рабочий вариант, просто стоит иметь это в виду.
